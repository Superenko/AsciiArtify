# Порівняльний аналіз інструментів локального розгортання Kubernetes: minikube, kind та k3d

Цей документ містить детальний аналіз локальних Kubernetes-платформ для стартапу **«AsciiArtify»** в межах підготовки системи локальної розробки та Proof of Concept (PoC) для автоматизації розгортання за допомогою ArgoCD.

---

## 1. Вступ

Для розробки програмного продукту з перетворення зображень у ascii-art за допомогою Machine Learning стартап «AsciiArtify» обрав Kubernetes як цільову платформу для розгортання та масштабування.

На етапі локальної розробки та підготовки PoC критично важливо мати швидке, стабільне та не вимогливе до ресурсів середовище. Ми розглянули три провідні інструменти:
1. **minikube** — класичне рішення, що запускає повноцінний Kubernetes-кластер на віртуальній машині або локально.
2. **kind (Kubernetes IN Docker)** — інструмент для запуску кластерів Kubernetes, де кожна нода представлена окремим Docker-контейнером.
3. **k3d** — обгортка над легким дистрибутивом **k3s** від Rancher, яка запускає його ноди всередині Docker-контейнерів.

## 2. Порівняльна таблиця характеристик

| Характеристика | minikube | kind | k3d |
|---|---|---|---|
| **Базовий рушій** | VM (Hyperkit, VirtualBox) або Docker / Podman | Docker / Podman | Docker / Podman (k3s контейнери) |
| **Архітектура нод** | Зазвичай одна нода (багатонодовість через додаткові ресурси) | Багатонодова архітектура (кожна нода — контейнер) | Багатонодова архітектура (кожна нода — контейнер) |
| **Швидкість запуску** | Повільно (1.5 - 3 хв) |  Швидко (1 хв) |  Дуже швидко (<30 сек) |
| **Споживання ресурсів** | Високе (мін. 2-3 ГБ RAM + накладні витрати на VM) |  Середнє (залежить від кількості нод в Docker) | Дуже низьке (k3s оптимізовано для IoT/Edge, ~500 МБ) |
| **Локальний Ingress** | Доступний через аддон `ingress` (Nginx) | Потребує ручного налаштування ExtraPortMappings |  Вбудований з коробки (Traefik на 80/443 портах) |
| **Зручність для CI/CD** | Складно (вимагає nested virtualization або складних контейнерів) |  Відмінно (розроблений для тестування K8s в CI) | Відмінно (легкі образи, швидкий старт в GitHub Actions) |
| **Локальний реєстр** | Вбудований аддон `registry` | Потребує додаткових скриптів для створення |  Створення реєстру однією командою (`--registry-create`) |
| **Підтримка архітектур** | amd64, arm64, 386 і т.д. | amd64, arm64 (Apple Silicon сумісний) | amd64, arm64 (Apple Silicon сумісний) |

## 3. Аналіз ризиків ліцензування Docker Desktop та альтернативи Podman

Оскільки AsciiArtify планує масштабуватись, необхідно врахувати фінансові та юридичні ризики, пов'язані з використанням **Docker Desktop**:

### Ризики ліцензування Docker Desktop:
> [!WARNING]  
> З серпня 2021 року ліцензійна угода Docker Desktop (Personal/Free) дозволяє безкоштовне використання лише для особистих цілей, некомерційних проєктів, навчання або малих компаній (менше 250 працівників **та** менше $10 млн річного доходу). 
> Якщо стартап «AsciiArtify» вийде на стадію комерційного успіху чи розширить команду, використання Docker Desktop вимагатиме платних ліцензій ($5-$24 за користувача на місяць).

### Альтернатива: Podman (Docker-less)
**Podman** — це безкоштовна, повністю відкрита (open-source) альтернатива Docker без демона (daemonless), яка використовує сумісні з OCI контейнери. Вона дозволяє повністю уникнути ліцензійних ризиків.

* **minikube:** має хорошу підтримку драйвера `podman` для macOS/Linux.
* **kind:** повністю підтримує Podman як рушій. Потрібно лише встановити змінну оточення `KIND_EXPERIMENTAL_PROVIDER=podman` перед створенням кластера.
* **k3d:** підтримує Podman (зокрема rootless-режим), проте для стабільної роботи на macOS потребує налаштування системного сокету Podman Machine (`podman system service`).

## 4. Переваги та недоліки інструментів

### 4.1. minikube
* **Переваги:**
  * Великий набір вбудованих додатків (аддонів), які вмикаються однією командою (`dashboard`, `ingress`, `metrics-server`).
  * Дуже широка та зріла спільнота, величезна кількість документації.
  * Можливість вибору різних драйверів віртуалізації.
* **Недоліки:**
  * Повільний запуск через необхідність ініціалізації віртуальної машини (якщо не використовувати bare-metal драйвер).
  * Високе споживання пам'яті та батареї на ноутбуках macOS.
  * Складне моделювання великих багатонодових кластерів для тестування високої доступності (High Availability).

### 4.2. kind
* **Переваги:**
  * Ідеальний інструмент для локального запуску тестів у CI/CD (GitHub Actions, GitLab CI).
  * Дуже швидкий та стабільний завдяки використанню ванільного Kubernetes в Docker.
  * Дозволяє легко створювати мультинодові топології через конфігураційні YAML-файли.
* **Недоліки:**
  * Немає вбудованого механізму аддонів (Ingress, Dashboard доводиться встановлювати вручну).
  * Потребує додаткового налаштування порту (ExtraPortMappings) на етапі створення кластера, щоб отримати доступ до Ingress з Mac.

### 4.3. k3d
* **Переваги:**
  *  **Найшвидший запуск кластера** на macOS (до 20-30 секунд).
  *  **Низьке споживання ресурсів** (під капотом полегшений k3s, у якому видалені хмарні провайдери та непотрібні драйвери).
  *  **Багатий функціонал з коробки:** вбудований балансувальник навантаження (load balancer) Traefik на портах 80/443, автоматичне створення локального реєстру однією опцією CLI.
  *  Чудова підтримка створення мультинодових та мультикластерних середовищ безпосередньо з CLI-аргументів.
* **Недоліки:**
  *  Використовує k3s, який хоч і сумісний з CNCF K8s на 100%, але деякі внутрішні компоненти (наприклад, Traefik замість Nginx Ingress) можуть відрізнятися від стандартного ванільного Kubernetes у production.

### Покроковий приклад розгортання «Hello World» у k3d

1. **Створення кластера з відкритими портами 80/443 для доступу з macOS:**
   ```bash
   k3d cluster create mycluster -p "8081:80@loadbalancer" -p "8443:443@loadbalancer"
   ```

2. **Розгортання тестового застосунку (Hello World):**
   Створіть маніфест `hello-world.yaml`:
   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: hello-app
   spec:
     replicas: 2
     selector:
       matchLabels:
         app: hello
     template:
       metadata:
         labels:
           app: hello
       spec:
         containers:
         - name: hello-container
           image: gcr.io/google-samples/hello-app:1.0
           ports:
           - containerPort: 8080
   ---
   apiVersion: v1
   kind: Service
   metadata:
     name: hello-service
   spec:
     type: ClusterIP
     ports:
     - port: 80
       targetPort: 8080
     selector:
       app: hello
   ```
   Застосуйте маніфест:
   ```bash
   kubectl apply -f hello-world.yaml
   ```

3. **Створення Ingress для доступу через вбудований Traefik:**
   Створіть маніфест `ingress.yaml`:
   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: Ingress
   metadata:
     name: hello-ingress
     annotations:
       ingress.kubernetes.io/ssl-redirect: "false"
   spec:
     rules:
     - http:
         paths:
         - path: /
           pathType: Prefix
           backend:
             service:
               name: hello-service
               port:
                 number: 80
   ```
   Застосуйте маніфест:
   ```bash
   kubectl apply -f ingress.yaml
   ```

4. **Тестування доступу з хост-машини (Mac):**
   ```bash
   curl localhost:8081
   ```
   *Результат:* Ви отримаєте відповідь `Hello, world! Version: 1.0.0` без будь-яких додаткових налаштувань port-forwarding!

## 6. Висновки та рекомендації для стартапу

Для стартапу «AsciiArtify» ми рекомендуємо обрати **k3d** як основний інструмент локальної розробки та проведення PoC.

### Обґрунтування вибору:
1. **Швидкість розробки:** Можливість перезапуску кластера менш ніж за 30 секунд дозволяє розробникам швидко експериментувати з конфігураціями без тривалого очікування.
2. **Продуктивність на macOS:** k3d майже не створює навантаження на систему порівняно з minikube на віртуальних машинах. Це критично, оскільки Machine Learning завдання локально вже потребуватимуть багато CPU/GPU ресурсів.
3. **Готовність до GitOps:** Вбудована Traefik-маршрутизація робить k3d чудово сумісним з ArgoCD та API Gateway (Ambassador), які є основою PoC та MVP даного проєкту.
4. **Мінімізація ліцензійних ризиків:** Використання k3d у парі з Podman дозволить компанії повністю захистити себе від можливих фінансових вимог з боку Docker Desktop у майбутньому при збільшенні штату компанії.
